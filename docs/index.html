짧게 자주 하는 운동을 놓치지 않게 기록하는 앱

PROJECT GTG는 푸쉬업·풀업·딥스를 하루 중 여러 번 가볍게 수행하는 GTG 방식에 맞춰 만든 앱입니다. 처음에는 기능을 더 넣는 쪽으로 생각했지만, 실제로는 “켜자마자 기록할 수 있는가”가 더 중요했습니다. 그 판단을 기준으로 화면과 구조를 계속 줄여갔습니다.

요약

실제로 바꿔본 것들

화면을 예쁘게 만드는 것보다, 사용자가 앱을 여는 순간 무엇을 해야 하는지가 더 중요했습니다. 처음 만든 모습에서 덜어내고 남긴 것들을 기준으로 정리했습니다.

첫 실행은 최대한 가볍게

GTG는 긴 운동 세션보다 짧은 세트를 자주 반복하는 방식입니다. 그래서 첫 화면에서 설명을 읽게 하기보다, 바로 오늘의 기록을 남길 수 있게 만드는 쪽을 우선했습니다.

서버 없이도 먼저 쓸 수 있게

이 앱의 핵심 기능은 운동 기록과 확인입니다. 계정이나 동기화가 없어도 가치가 있어야 한다고 봤습니다. 그래서 기록은 로컬에 먼저 저장하고, 서버 연동은 나중에 켤 수 있는 구조만 남겼습니다.

기능은 나누고, 저장 방식은 감췄습니다

대시보드, 캘린더, 코치, 설정이 서로의 내부 구현을 직접 알지 않도록 나눴습니다. 화면은 Riverpod 상태를 보고, 저장 방식은 repository 계층 뒤로 숨겼습니다.

수정 후에는 테스트로 확인

화면과 흐름을 계속 줄이다 보니, 의도치 않게 기록/설정/알림이 깨지지 않는지 확인할 기준이 필요했습니다. 위젯/유닛/레이아웃 테스트를 나눠두고, 최근 기준 전체 테스트는 115개 통과, 2개 스킵 상태입니다.

결정

처음과 달라진 부분

처음에는 온보딩, 서버 동기화, 설정 항목을 더 적극적으로 넣었습니다. 만들다 보니 지금 버전에 필요한 것과 나중에 붙여도 되는 것이 갈렸습니다.

온보딩 제거

처음에는 운동 선택과 기준 반복 수를 받는 온보딩이 있었습니다. 그런데 운동 앱을 처음 켠 사람에게 필요한 건 설명보다 “한 세트 기록해보기”라고 보고, 첫 진입은 바로 홈으로 바꿨습니다.

첫 진입마찰 줄이기

서버 기능 보류

동기화 기능을 붙일 수 있게 PocketBase 연동 코드는 준비했지만, 지금 버전에서는 서버를 운영하지 않기로 했습니다. 기록 앱은 인터넷이 없어도 동작해야 하고, 초기에는 운영비보다 안정성이 더 중요하다고 봤습니다.

운영비 보류로컬 저장

코치 기능은 로컬 규칙부터

GTG Coach는 먼저 로컬 규칙으로 추천을 만듭니다. 기록이 며칠 비었는지, 기준 반복 수가 오래됐는지 같은 단순한 신호부터 사용하고, 나중에 서버 추천으로 바꿔도 화면 모델은 유지되게 했습니다.

확장 가능로컬 대안

화면

핵심 화면

각 화면은 한 가지 역할만 뚜렷하게 갖도록 나눴습니다.

UX 메모

화면을 이렇게 잡은 이유

운동 중에 앱을 오래 들여다보지 않는다는 전제로 화면을 잡았습니다.

홈에서는 바로 기록

홈에서는 오늘 몇 세트를 했는지 보고 바로 추가할 수 있어야 합니다. 자세한 설정이나 설명은 뒤로 빼고, 기록 버튼과 오늘 요약을 먼저 보이게 했습니다.

운동 중 보기 편한 어두운 화면

운동 중 잠깐 확인하는 앱이라 너무 밝은 화면은 부담스럽다고 느꼈습니다. 그래서 다크 톤을 기본으로 두고, 중요한 숫자와 버튼만 눈에 띄게 만들었습니다.

설정은 목적별로 나누기

설정 화면에 기능이 계속 쌓이면서 한 번 정리가 필요했습니다. 코치, 리마인더, 전체 기록처럼 목적이 다른 항목은 별도 화면으로 빼서 관리 화면을 가볍게 했습니다.

설명은 사용 흐름 안에서

GTG를 모르는 사람도 처음부터 긴 설명을 읽을 필요는 없다고 봤습니다. 대신 홈과 코치 화면에서 필요한 문장만 짧게 보여주고, 사용하면서 이해하게 만들었습니다.

구현

구현 방식

화면보다 오래 고민한 부분은 상태와 저장소의 경계였습니다.

Presentation
DashboardScreen, CalendarScreen, GtgCoachScreen, SettingsScreen으로 화면을 나눴습니다. 반복되는 카드, 여백, 색상은 GtgUi, GtgTheme 쪽으로 모았습니다.
State
상태 관리는 flutter_riverpod를 사용했습니다. 화면은 provider를 읽고, 저장·계산·알림 처리는 각 기능의 state 계층에서 맡도록 분리했습니다.
Domain
GTG Coach 정책, 운동 통계, 리마인더 계산은 화면 밖으로 빼서 유닛 테스트하기 쉽게 만들었습니다.
Data
WorkoutLogRepository, UserPreferencesRepository 같은 인터페이스로 저장소를 감쌌습니다. 현재는 로컬 저장이 기본이고, PocketBase는 설정값이 있을 때만 동기화됩니다.
Ops
GitHub Pages의 version.json으로 업데이트 안내를 제공하고, CI에서 format/analyze/test/build를 확인합니다.

라우팅

go_router의 StatefulShellRoute로 홈/캘린더/설정 탭을 구성했습니다.

저장소

저장소 실패 시 기본값으로 돌아가고, 손상된 JSON은 격리하도록 처리했습니다.

다국어

ARB 기반으로 한국어/영어 문구를 관리합니다.

남긴 기준

PROJECT GTG는 기능을 계속 더하기보다, 사용자가 바로 기록할 수 있는 흐름을 우선한 앱입니다. 서버 연동이나 온보딩처럼 넣을 수 있는 기능도 현재 가치에 맞지 않으면 보류했고, 그 결정이 코드 구조와 테스트에도 남도록 정리했습니다.
